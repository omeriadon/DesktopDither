# Desktop overlay layering research

Research date: 2026-10-29. Target: macOS 27.2 on M2 MacBook Air. Public documentation and the installed macOS 27.0 SDK were inspected. The runtime observations below were collected separately by the primary agent on the target Mac; they are observations, not API guarantees.

## Current implementation scope

The user will supply the visual content. The app therefore ships only a transparent, empty AppKit placeholder and its window/settings host. No snow, sparkles, animation, emitter, or rendering loop is included. Renderer comparisons below are research options, not selected or shipped effects. The placeholder exposes a lifecycle hook for the eventual view; its renderer-specific pause behavior must be implemented when that view is supplied.

## Recommended architecture

Use one transparent, borderless AppKit window per `NSScreen`, with an `NSView` hosting a Core Animation layer tree. Set its level to `CGWindowLevelForKey(.desktopWindow) + 1`; query `.desktopIconWindow` too and assert the chosen value is below it. Use the full `screen.frame`, including the regions behind Dock/menu bar, rather than `visibleFrame`. This preserves the current wallpaper and requires no screenshot capture, desktop-image replacement, Accessibility access, Dock injection, or private WindowServer calls. The recommendation is an engineering choice using public APIs; Apple does not document a dedicated third-party animated wallpaper overlay contract. [Window levels](https://developer.apple.com/documentation/appkit/nswindow/level-swift.property), [Core Graphics level keys](https://developer.apple.com/documentation/coregraphics/cgwindowlevelkey), [desktop icon level](https://developer.apple.com/documentation/coregraphics/cgwindowlevelkey/desktopiconwindow), [screen frame](https://developer.apple.com/documentation/appkit/nsscreen/frame).

Keep `isOpaque = false`, a clear window background, and `hasShadow = false`. Otherwise the overlay can cover the underlying wallpaper. `ignoresMouseEvents = true` makes the entire window click-through. Override `canBecomeKey` and `canBecomeMain` to return false, and show it without a key-window or application-activation call. `.nonactivatingPanel` is explicitly an `NSPanel` style, not a documented way to make an ordinary `NSWindow` nonactivating. Either a borderless `NSWindow` with these overrides or a deliberately configured nonactivating `NSPanel` is possible; prefer the simpler window for an entirely passive effect. [Mouse transparency](https://developer.apple.com/documentation/appkit/nswindow/ignoresmouseevents), [key eligibility](https://developer.apple.com/documentation/appkit/nswindow/canbecomekey), [main eligibility](https://developer.apple.com/documentation/appkit/nswindow/canbecomemain), [nonactivating panel](https://developer.apple.com/documentation/appkit/nswindow/stylemask-swift.struct/nonactivatingpanel).

The open-source wallpaperd implementation independently uses the same `desktopWindow + 1` level, all-Spaces/stationary/cycle-exclusion behavior, input transparency, and explicit focus refusal. Its opaque video background is inappropriate for an overlay that must retain the current wallpaper; its layering approach is relevant. This is implementation evidence rather than an Apple guarantee. [Pinned source, DesktopWindow.swift](https://github.com/MufanQiu/wallpaperd/blob/068c01774bbb981b3a30e0d587a68573966187a2/Sources/WallpaperDaemon/DesktopWindow.swift).

The primary agent queried public Core Graphics level values and existing window metadata on macOS 27.2. See the separate `Research/window-levels.json` evidence artifact when available.

| Existing WindowManager windows | -2147483624 |
| `CGWindowLevelForKey(.desktopWindow)` | -2147483623 |
| Proposed overlay (`desktopWindow + 1`) | -2147483622 |
| Finder desktop icons / `.desktopIconWindow` | -2147483603 |

| Notification Center desktop widget-sized windows | -2147483601 |
| Normal windows | 0 |
| Dock | 20 |

This snapshot supports the required ordering on this Mac: wallpaper, overlay, Finder icons, desktop widgets, ordinary apps, Dock/menu bar. Metadata alone does not verify animation, Space transitions, or every widget state. Apple documents the icon level but not a stable desktop-widget window level. Recheck visually with real desktop widgets and after OS updates. There is no reason to choose `.desktopIconWindow` itself: same-level ordering may put effects over icons. `.desktopIconWindow - 1` leaves less separation from system desktop surfaces than `desktopWindow + 1` and adds no benefit here.

The installed SDK explains why levels must be queried rather than copied as numbers: numeric values can change between OS versions. Local evidence: `/Library/Developer/CommandLineTools/SDKs/MacOSX.sdk/System/Library/Frameworks/CoreGraphics.framework/Headers/CGWindowLevel.h`, lines 17–20, 22–53, and 59–80. The legacy macros place desktop icons 20 levels above the desktop and list ordinary windows, Dock, and menu above both; use `CGWindowLevelForKey` at runtime instead.

## Spaces, fullscreen, Stage Manager, and displays

Use the initial collection behavior `[.canJoinAllSpaces, .stationary, .ignoresCycle, .fullScreenNone]`. Their contracts are distinct: all Spaces permits cross-Space presence; stationary keeps the window unaffected by Mission Control; ignoresCycle excludes window cycling; fullScreenNone prevents this window becoming a native fullscreen window. It does **not** promise to hide the overlay from every other application's fullscreen Space. Do not combine stationary with transient or managed; the SDK marks them mutually exclusive. [All Spaces](https://developer.apple.com/documentation/appkit/nswindow/collectionbehavior-swift.struct/canjoinallspaces), [stationary](https://developer.apple.com/documentation/appkit/nswindow/collectionbehavior-swift.struct/stationary), [cycle exclusion](https://developer.apple.com/documentation/appkit/nswindow/collectionbehavior-swift.struct/ignorescycle), [fullscreen none](https://developer.apple.com/documentation/appkit/nswindow/collectionbehavior-swift.struct/fullscreennone).

Do not opt into `.fullScreenAuxiliary` or `.canJoinAllApplications` for the initial desktop-only implementation. Apple describes the latter as allowing eligible windows to join other applications' fullscreen Spaces and Stage Manager sets. Low window level is the ordering mechanism; fullScreenNone is not an alternative to setting that level. Public collection behavior expresses policy but does not expose an exhaustive list of other apps' fullscreen Spaces. Validate actual fullscreen, Split View, Stage Manager, Show Desktop, Mission Control, and Space transitions. [Cross-application behavior](https://developer.apple.com/documentation/appkit/nswindow/collectionbehavior-swift.struct/canjoinallapplications), local `AppKit.framework/Headers/NSWindow.h`, lines 90–149.

Create independent windows from current `NSScreen.screens`, and reconcile them when `NSApplication.didChangeScreenParametersNotification` arrives. The reported target configuration has displays sized 1710×1112 and 1920×1080 points. Use each screen's complete global frame, and local view bounds for layers; do not assume screens start at the same origin or share scale. Test with “Displays have separate Spaces” both enabled and disabled, and with one display fullscreen while the other shows the desktop. Reconcile geometry on wake and display reconnection. [Display configuration changes](https://developer.apple.com/documentation/appkit/nsapplication/didchangescreenparametersnotification), [separate Spaces](https://developer.apple.com/documentation/appkit/nsscreen/screenshaveseparatespaces).

## Renderer and power policy

For sparse snow/rain, start with a single `CAEmitterLayer` per display and small shared sprite images; use a few standalone animated `CALayer`s for glows. This avoids an application timer that updates positions and redraws a SwiftUI Canvas every frame. Core Animation executes configured animations and generally uses graphics hardware; Apple explicitly warns that using it does not guarantee better performance. Measure the chosen effect on the target machine. [Emitter layer](https://developer.apple.com/documentation/quartzcore/caemitterlayer), [Core Animation overview](https://developer.apple.com/documentation/quartzcore), [performance guidance](https://developer.apple.com/library/archive/documentation/Cocoa/Conceptual/CoreAnimation_guide/ImprovingAnimationPerformance/ImprovingAnimationPerformance.html).

Budget particle count and blended area, not just app CPU. As an estimate, a steady emitter's live population is approximately births per second multiplied by average lifetime; scale density to screen area and avoid large overlapping translucent sprites. `birthRate` is particles created per second, while lifetime governs how long they persist. Large transparent full-screen surfaces and effects can still consume compositor/GPU power. Low app CPU alone cannot establish low energy use. [Birth rate](https://developer.apple.com/documentation/quartzcore/caemittercell/birthrate), [lifetime](https://developer.apple.com/documentation/quartzcore/caemittercell/lifetime), [Mac graphics energy costs](https://developer.apple.com/library/archive/documentation/Performance/Conceptual/power_efficiency_guidelines_osx/FundamentalConcepts.html).

Canvas is a legitimate immediate-mode drawing API, but pairing it with a repeating timer or animation timeline still requires ongoing app drawing work. Metal is appropriate when profiling demonstrates a need for dense particles, custom simulation, shaders, or an explicit frame-rate budget; it adds renderer complexity. `MTKView` exposes `preferredFramesPerSecond` and `isPaused`; a 30 Hz preference is a reasonable initial experiment for gentle effects, not a measured guarantee. CAEmitterLayer has no comparable public per-emitter frame-rate control in the inspected SDK. [Canvas](https://developer.apple.com/documentation/swiftui/canvas), [Metal view modes](https://developer.apple.com/documentation/metalkit/mtkview), [preferred frame rate](https://developer.apple.com/documentation/metalkit/mtkview/preferredframespersecond), [pause](https://developer.apple.com/documentation/metalkit/mtkview/ispaused).

Pause each display's rendering when that overlay's `occlusionState` lacks `.visible`. Use window-level state, because opening the settings window can make the app visible while its desktop overlays are covered. Visibility is conservative: even a transparent window can count as visible. Do not use app deactivation as the pause signal; a passive wallpaper app is normally inactive. [Apple's occlusion guidance](https://developer.apple.com/library/archive/documentation/Performance/Conceptual/power_efficiency_guidelines_osx/WorkWhenVisible.html), local `AppKit.framework/Headers/NSWindow.h`, lines 183–190.

Also pause for system sleep, display sleep, and an inactive user session; register the corresponding observers with `NSWorkspace.shared.notificationCenter` and re-evaluate state after wake/reactivation. These session notifications describe user-session switching; they are not a documented universal “screen locked” callback. Use supported occlusion/sleep/session signals together rather than treating one notification as proof of lock state. [Display sleep](https://developer.apple.com/documentation/appkit/nsworkspace/screensdidsleepnotification), [system sleep](https://developer.apple.com/documentation/appkit/nsworkspace/willsleepnotification), [session deactivation](https://developer.apple.com/documentation/appkit/nsworkspace/sessiondidresignactivenotification).

Setting emitter `birthRate = 0` stops births but lets existing particles continue; it is not an immediate rendering pause. For immediate idle, freeze the parent layer timeline with preserved local timing or detach the effect layer; restart or correctly rebase timing when resuming. The SDK explicitly documents zero layer speed as a pause mechanism. Local evidence: `QuartzCore.framework/Headers/CAMediaTiming.h`, lines 48–59. [Layer speed](https://developer.apple.com/documentation/quartzcore/camediatiming/speed), [time offset](https://developer.apple.com/documentation/quartzcore/camediatiming/timeoffset).

Observe `NSProcessInfoPowerStateDidChange` and `thermalStateDidChangeNotification`. Query current values at startup too. For this optional effect, pause in Low Power Mode and serious/critical thermal states; reduce density at fair thermal state. Respect Reduce Motion with a static or disabled effect. These are proposed app policies consistent with Apple's energy/accessibility guidance. Do not request activity assertions to prevent App Nap or display sleep. [Power/thermal response](https://developer.apple.com/documentation/xcode/responding-to-power-notifications), [Reduce Motion](https://developer.apple.com/documentation/appkit/nsworkspace/accessibilitydisplayshouldreducemotion).

## Private alternatives and lock screen boundary

SkyLight APIs can manipulate window tags, sublevels, and Spaces. Yabai's source illustrates direct `SLSSetWindowTags` and `SLSSetWindowSubLevel` calls; its scripting addition loads into Dock to perform privileged operations on windows/Spaces owned by other processes. This is a different problem from positioning a window the app owns. Its manual documents SIP restrictions, and its changelog records OS-version-specific repairs. None of this is necessary for the proposed overlay. Do not infer that every private call requires injection, or that manipulating arbitrary other apps' windows is supported by ordinary NSWindow APIs. [Yabai payload](https://github.com/asmvik/yabai/blob/master/src/osax/payload.m), [private declarations](https://github.com/asmvik/yabai/blob/master/src/misc/extern.h), [scripting-addition manual](https://github.com/asmvik/yabai/blob/master/doc/yabai.asciidoc), [maintenance evidence](https://github.com/asmvik/yabai/blob/master/CHANGELOG.md).

Keep the feature within the logged-in desktop session. The researched public window APIs provide no contract for inserting arbitrary app content into the secure lock/login UI. This architecture must not promise animated effects on that surface. Do not inject into Wallpaper, Dock, loginwindow, or WindowServer, modify Apple's wallpaper database, or elevate the overlay to screen-saver/security UI levels. Hiding or pausing during lock-related occlusion is compatible with the design; making a secure lock-screen renderer is a separate unsupported requirement under this architecture.

## Remaining verification

- Verify a transparent proof-of-concept visually above the current still/video wallpaper and below all actual desktop widgets/icons, with desktop click, selection rectangle, widget interaction, Dock hover, and menu interaction intact.
- Verify Spaces, Mission Control, Show Desktop, Stage Manager, fullscreen/Split View, display disconnect, scale changes, sleep/wake, lock/unlock, and fast user switching. The metadata snapshot is insufficient for these transitions.
- Measure app and WindowServer CPU, GPU/compositor work, memory, and energy with one/two displays, visible/covered desktop, and battery/Low Power Mode. No measured fps, watts, CPU percentage, or battery-life claim has been established by this research.
